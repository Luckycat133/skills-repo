# Acceptance criteria

A migration succeeds only when the intended user content is preserved in a target
that recognizes it, with no silent scope, activation, invocation or permission
widening. Exact unsupported fields become explicit losses or reviewed drafts.

Required: source unchanged; unrelated target settings/comments preserved; each
independent nonconflicting object handled; same-content no-op; secrets/auth/trust
excluded; executable content inactive until separately approved; bounded reads;
preview zero target writes; clear distinction between syntax and runtime proof.

All selected context categories must be accounted for, including prompts, commands,
agents, hooks, workflows, packages and user-authored memory. Names alone do not prove
semantics. Unknowns are recorded and resolved from official/local evidence.

Repository checks: main entrypoints stay short; all package links resolve; catalog
routes every historical identifier; sources and evidence levels are explicit;
real-client status is not invented; package contains only approved guidance and
templates, no dev/evals/history/code; archive creation is repeatable and refuses
clobbering. These checks are not substitutes for client-tests.md.

Do not certify product-pair Cartesian combinations. A native client pass applies
only to the tested version/profile/category and recorded environment. Publication
requires separate approval after real results are reviewed.
